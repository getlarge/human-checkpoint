# Committed hardware evidence

`human-checkpoint-proof.json` is a real `human-checkpoint-proof:v1` record. Both
signatures in it were produced by one physical YubiKey 5.8 using previewSign,
during an actual ceremony on 2026-08-05 in the local demo environment. Nothing
in it is mocked, replayed, or generated by a test fixture.

It is committed so the central claim of this project can be checked by anyone,
with no YubiKey, no Docker, no MoltNet, no API keys, and no network:

```bash
pnpm install --frozen-lockfile
pnpm run verify:evidence
```

That command verifies both ESP256 signatures, confirms the two decisions used
different request-scoped ARKG keys, then mutates one character of the field
note **in a copy** and confirms verification fails.

## What it proves, and what it does not

It proves that two distinct hardware ceremonies happened, that each bound the
exact canonical bytes shown to the technician, and that the two decisions were
signed under different derived public keys.

It does not prove the maintenance decision was correct, and it is not anonymous
signing. The record deliberately retains the claimant and credential
identifiers so a decision stays attributable. That is request-scoped key
separation and exact-byte accountability, not unlinkability.

## Contents

Every identifier is from the throwaway local demo environment: synthetic team,
technician, and support-request records created by `pnpm run setup:local`. The
record holds only public keys, signatures, canonical messages, digests, and
those identifiers. It carries no token, cookie, secret, or private key
material.

## Refreshing it

Export a new record from the dashboard after a completed run, then replace this
file. Keep the tamper check pointed at text that exists in the new field note —
`scripts/verify-evidence.mjs` looks for a known substring and fails loudly if
the record no longer contains it.
